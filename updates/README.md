# Dependency updates

Every onboarded repo gets a weekly check of everything it pins, on Monday
morning Melbourne time (`updates/defaults.yml`). Updates arrive as pull
requests (or, where a move needs a deliberate change, as an issue), opened as
a GitHub App so the repo's CI runs on them. **A person reviews and merges
every one: nothing merges automatically.**

- **Dependabot** handles the ecosystems it does well (Cargo, npm, pip, Go
  modules, GitHub Actions). Its config, `.github/dependabot.yml`, is
  generated by infra.
- **Infra's checks** handle the rest: toolchains, base images, release
  binaries, anything pinned in a Dockerfile or a data file. Each repo
  describes those pins in **`.github/updates.yml`**, a committed file.

A repo opts in with `onboard-repo.sh --updates`. That needs no per-repo
secrets or settings beyond the `BAO_ADDR` variable onboarding already sets.

```
app repo                                   infra
.github/workflows/dependency-updates.yml   .github/workflows/dependency-updates.yml (reusable)
  (generated caller: schedule +    ──────▶   plan     → validates .github/updates.yml, builds the matrix
   workflow_dispatch)                        check ×N → runs each check with NO secrets, uploads a patch + PR text
.github/updates.yml                          collect  → which checks want a PR or an issue
  (what's pinned where)                      publish  → infra steps only: OpenBao login, app token for this
.github/dependabot.yml                                  repo, applies the patch, opens/updates the PR or issue
  (generated from updates.yml)               report   → one "check failed" issue per repo
scripts/... (custom checks, optional)      updates/   (this engine: Python, standard library)
```

## One-time setup (per GitHub owner)

### 1. The GitHub App

PRs opened with a workflow's own `GITHUB_TOKEN` don't trigger other
workflows, so CI wouldn't run on them. They're opened as one app instead,
shared by every repo.

1. Your profile → Settings → Developer settings → GitHub Apps → **New GitHub App**.
   - Name: anything (e.g. `<you>-updates`). Its slug is in its URL,
     `github.com/apps/<slug>`.
   - Homepage URL: this repository. **Webhook: untick Active.**
   - Repository permissions: **Contents: Read and write** and **Pull requests:
     Read and write**. Nothing else (Metadata: read-only is added
     automatically). It has **no Workflows permission**, on purpose: no
     update can change `.github/workflows/`.
   - Where can it be installed: **Only on this account.**
2. On the app's page, note the **Client ID** and **Generate a private key**
   (a `.pem` downloads).
3. **Install App** on your account → **Only select repositories**. Add
   repos one at a time: onboarding adds each repo it onboards (below).
4. Put the credentials in OpenBao (`bao-day` first), then delete the key file:
   ```bash
   bao kv put -mount=kv updates/github-app client_id=<Client ID> private_key=@app.pem
   shred -u app.pem
   ```
5. Set `UPDATES_APP=<slug>` in your laptop's `config.env`, and run
   `bao-configure`. It creates the `updates` policy and JWT role (below).

The key is at `kv/updates/github-app`, **not** under `kv/shared/`. Every
onboarded repo's own `main` workflows can read `kv/shared/*` (role
`deploy`), and anyone holding this key can mint tokens for every repo the
app is installed on.

### 2. Who can read the key

`bao-configure` creates the role `updates`. Its only policy is `read` on
`kv/data/updates/github-app`, and it's bound to:

```json
"bound_audiences": ["<BAO_ADDR>"],
"bound_claims": {
  "repository_owner": "<GH_OWNER>",
  "ref": "refs/heads/main",
  "job_workflow_ref": "<INFRA_REPO>/.github/workflows/dependency-updates.yml@refs/heads/main"
}
```

- `job_workflow_ref` is the workflow file a job's code comes from. For a
  job in a reusable workflow it names the reusable workflow, not the
  caller. So only **infra's own workflow, from infra's `main`**, running
  for a repo's `main` branch, can log in. A repo's own workflow, or infra's
  workflow at another branch, can't. These are exact matches
  (`bound_claims_type: string`), so no glob is needed.
- Within that workflow, only the `publish` job has `id-token: write`, and
  its steps are fixed in infra. It never runs anything from the caller
  repo. The `check` jobs, which may run the repo's own code, have no
  OpenBao access and no secrets.
- The JWT's audience is the OpenBao address itself. A caller that passed
  some other `bao_addr` would get a JWT addressed to that host, which the
  real OpenBao refuses.
- The token minted from the key is limited to **the calling repository**,
  with only `contents: write` and `pull-requests: write`, and lasts an hour.

## Onboarding a repo

```bash
onboard-repo.sh jdoe/api --backend --target oracle --updates   # with a deploy pipeline
onboard-repo.sh jdoe/lib --updates                             # updates only (e.g. a library)
onboard-repo.sh jdoe/api --updates --pr                        # as a pull request
```

With `--updates`, onboarding:

- writes the caller `.github/workflows/dependency-updates.yml` (schedule from
  `updates/defaults.yml`; `workflow_dispatch` with `dry_run` and `fail`). In
  infra itself that path is the reusable workflow, so the caller is
  `dependency-updates-caller.yml`;
- writes a starter `.github/updates.yml` if there's none (`version: 1`,
  `checks: []`), and the generated `.github/dependabot.yml`;
- adds the repo to the app's installation through the GitHub API (that
  endpoint needs a classic personal access token in `gh`; otherwise it says
  how to do it by hand);
- turns on Dependabot alerts and security updates;
- offers to delete old per-repo secrets (`UPDATES_APP_CLIENT_ID`,
  `UPDATES_APP_PRIVATE_KEY`, `UPDATES_TOKEN`).

Then describe the repo's pins in `.github/updates.yml`, and run the workflow
by hand with **dry run** ticked (Actions → Dependency updates → Run
workflow). Each check's job summary shows the diff and PR text it would
open.

Repos onboarded without `--updates` don't change at all.

## `.github/updates.yml`

[`examples/updates.yml`](../examples/updates.yml) shows every option. In short:

```yaml
version: 1

dependabot:              # additions to the detected ecosystems
  npm:
    - directory: /frontend
      ignore:
        - dependency-name: "@types/node"
          update-types: [version-update:semver-major]

checks:
  - name: rust           # names the branch updates/rust (lower case, digits, dashes)
    type: rust-toolchain
    edits:
      - { file: rust-toolchain.toml, pattern: '^channel = "(?P<version>[\d.]+)"$' }
      - file: server/Dockerfile
        pattern: '\brust:(?P<version>[\d.]+)-slim-\w+'
        docker_image: library/rust     # the new tag must exist before a PR is opened
    notes: New Clippy lints can fail CI on this PR.
```

The `plan` job validates the file and reports every problem at once, with
its place (`checks[2].edits[0].pattern: …`). Locally: `python3
<infra>/updates/cli.py validate` in the repo.

### Edits

Each edit is a `file` and a `pattern`: a Python regular expression in
multi-line mode (single-quote it in YAML). Named groups say what to read
and rewrite:

| Group | Meaning |
|---|---|
| `version` | The pinned version. Every edit of a check must agree on it ("disagrees with itself" otherwise), which is how the check reads the current version. |
| `sha256`, `size` | `github-release` only, with `asset`: the asset's SHA-256 and size in bytes. |
| `tag` | Optional: the image tag `docker_image` checks. By default that's the text after the match's last `:` (`rust:1.2.3-slim-trixie` → `1.2.3-slim-trixie`), or else the version. |

Each pattern must match exactly once, or `count` times. Otherwise the
check fails and says the pin has moved. Only the named groups change.
Edits can't target `.github/workflows/`, because the app can't change
workflows. Move such a pin into a data file the workflow reads (a
`.nvmrc`, `rust-toolchain.toml`, a version file, `pins.env`) and edit that.

`docker_image` (any edit): after rewriting, the new tag must exist in that
registry (Docker Hub, GHCR, Quay…). If it doesn't yet, the check proposes
nothing this week (with a warning), because images often follow a release
by a day. In `issue` mode it's noted in the issue instead.

### Check types

| Type | Latest version from | Options |
|---|---|---|
| `rust-toolchain` | Rust's stable channel manifest | |
| `node-lts` | `nodejs.org/dist/index.json`, the newest LTS **major** | Pins hold a major (`24`) |
| `chocolatey` | the Chocolatey package feed | `package` |
| `debian-stable` | `deb.debian.org`'s stable `Release` | Pins hold a codename; compared by Debian version. Usually `mode: issue`. |
| `github-release` | a repo's newest 100 releases, the highest version | `repo`, `tag_pattern` (a `version` group; default `v1.2.3` or `1.2.3`), `prerelease` (default false). Edits may have `asset: <name>` (`{version}`, `{tag}` are filled in): the SHA-256 comes from the release API's digest **and** a download, which must match. |
| `docker-tag` | an image's tags, filtered by `tag_pattern`, compared as versions | `image` |
| `custom` | the repo's own command | `run` (below) |

Every type also takes `mode` (`pr`, the default, or `issue`) and `notes`
(text appended to the PR or issue, e.g. what to test). PR bodies list the
old and new version, the release notes and comparison links, every changed
file, and asset hashes. Issues show the change as a diff to make by hand.

### Custom checks

For an update only one repo understands (e.g. delegation's llama.cpp pins,
several archives with hashes and renamed assets):

- infra runs `run` with bash, from the repo root, **in the check job: no
  secrets, no OpenBao, no write token**. It sets `UPDATE_OUT` (an empty
  directory), `UPDATE_CHECK` (the check's name), and `UPDATE_DRY_RUN=1` in
  dry runs (skip slow verification such as big downloads, and say so in
  the body). `GITHUB_TOKEN` is the workflow's read-only token, for API rate
  limits.
- If there's an update, the command edits files in the working tree.
- It writes `$UPDATE_OUT/result.json`:
  `{"result": "none" | "pr" | "issue", "title": "…", "version": "…"}`.
  With `pr` or `issue` it also writes `$UPDATE_OUT/body.md`. Then it exits 0.
- A non-zero exit fails the check. So does `pr` with no file changed, a
  change with `none` or `issue`, or any change under `.github/workflows/`.
- Infra makes the patch from the working tree and opens the PR. The
  command never handles git, tokens or GitHub.

### Dependabot, generated

`.github/dependabot.yml` is rendered from the repo's files: `Cargo.lock` →
`cargo`; `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml` → `npm` per
directory; any workflow → `github-actions`; `go.sum` → `gomod`;
`requirements*.txt`, `pyproject.toml` → `pip`. Directories under
`node_modules/`, `vendor/`, `target/` and `third_party/` are skipped. Then
the `dependabot:` entries of `updates.yml` are merged in. An entry adds a
directory, sets extra options (`ignore`, `allow`, `labels`, `groups`, …),
or turns a detected one off with `enabled: false`. The schedule is
`updates/defaults.yml`'s, the same for every repo. Minor and patch updates
are grouped per ecosystem. The `docker` ecosystem is never detected,
because image versions often move with other files. Add it per directory
where an image is all that changes.

Every run renders it again. If the repo's file differs, a PR on
`updates/dependabot-config` brings it in line.

## How a run works

- **plan** checks out the repo and infra (at `infra_ref`), validates
  `updates.yml`, and outputs the matrix: every check, plus
  `dependabot-config`.
- **check** (one job each, `fail-fast: false`) runs the check and uploads
  `update-<name>`: `result.json`, `body.md`, and for a PR `changes.patch`.
  In a dry run its job summary has the diff and the text, and nothing is
  published.
- **publish** (only for checks that want a PR or issue) applies the patch.
  It refuses anything under `.github/workflows/` or `.git/`, symlinks, and
  paths outside the tree, and checks all of that *before* any credential
  exists. Then it logs in to OpenBao, mints the token, and runs
  `peter-evans/create-pull-request` on `updates/<name>` with signed commits.
  A later run updates the same PR. Issues are found by a hidden
  `<!-- dependency-update:<name> -->` marker and edited in place. They're
  opened with the workflow's own token (an issue doesn't need to trigger
  CI), so the app needs no Issues permission.
- **report** opens or updates one **"Dependency update check failed"**
  issue when any job failed. It closes that issue on the next fully
  successful run, and leaves it alone when jobs were cancelled.

Runs of the same repo queue (`concurrency`). The caller grants
`contents: read`, `issues: write`, `actions: read`, `id-token: write`.

## Running checks locally

From a clone of the repo (needs Python 3.11+, and `yq` or PyYAML):

```bash
python3 ~/infra/updates/cli.py validate
python3 ~/infra/updates/cli.py check rust            # prints the diff and the PR text
GITHUB_TOKEN=$(gh auth token) python3 ~/infra/updates/cli.py check cloudflared
python3 ~/infra/updates/cli.py check llama-cpp --dry-run
python3 ~/infra/updates/cli.py dependabot            # what .github/dependabot.yml should be
```

Locally, `check` never changes your files. A custom check runs in a copy of
the repo. The engine's tests run offline, in infra's CI too:
`python3 -m unittest discover -s updates/tests`.

## Troubleshooting

**Every check that finds an update fails at "OpenBao login (role
updates)".** Usually one of these:

- `kv/updates/github-app` is missing, or `bao-configure` wasn't run after
  this was added.
- The run isn't on `main`. A `workflow_dispatch` from another branch has
  `ref` `refs/heads/<branch>`.
- `INFRA_REPO` in `config.env` doesn't match the caller's `uses:` (the case
  matters).
- The caller calls infra at a ref other than `@main`.

OpenBao's error names the claim that didn't match (`claim "job_workflow_ref"
does not match …`). To see a real token's claims, add this job to a scratch
branch of a repo and run it:

```yaml
  claims:
    runs-on: ubuntu-latest
    permissions: { id-token: write }
    steps:
      - run: |
          curl -sS -H "Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
            "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=test" | jq -r .value | cut -d. -f2 \
            | tr '_-' '/+' | base64 -d 2>/dev/null | jq '{repository, ref, job_workflow_ref, aud}'
```

In a reusable workflow, `job_workflow_ref` is
`<owner>/infra/.github/workflows/dependency-updates.yml@refs/heads/main`,
exactly as the role binds it.

**"Not Found" or "Resource not accessible by integration" at "App token".**
The repo isn't in the app's installation. Add it (app → Configure →
Repository access), or re-run `onboard-repo.sh --updates`.

**A check fails with "the pin has moved".** The file changed shape. Fix the
pattern in `.github/updates.yml`.

**Testing the failure issue.** Run the workflow with `fail: <check name>`.
That opens the issue, and the next normal run closes it.
